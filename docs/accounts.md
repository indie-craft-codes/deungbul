# 계정과 로그인 설계안

2026-11-23 작성(2026-11-27 현행화: 경로, 기기 옮기기, 인증 접점). 설계만 있고 계정은 구현하지 않았다. 아래 "정할 것"이 정해진 뒤에 구현한다. 그 사이에 들어간 것: 기기 옮기기(아래), 인증을 갈아 끼우는 접점(2026-11-27 묶음 2: 화면 `AuthProvider`·`guestAuth`, 서버 `ServerAuth`·`startServer({ auth })`. 지금은 손님만, [making-a-game.md](making-a-game.md) 17절).

## 결론

- **지금처럼 로그인 없이 바로 시작하는 것은 유지한다.** 링크를 누르면 곧바로 게임이 시작되는 것이 브라우저 게임의 가장 큰 장점이다.
- **계정은 "내 캐릭터를 잃지 않게 지키는 것"으로 내놓는다.** 손님으로 하다가, 원할 때 계정에 연결한다. 연결하면 다른 기기에서도 같은 캐릭터로 들어온다.
- **첫 로그인 수단은 소셜 로그인 하나 또는 둘로 시작하길 권한다.** 비밀번호를 직접 받지 않아서 보관과 유출의 책임이 작고, 만들 것이 가장 적다. 어느 서비스로 할지는 정해야 한다.
- 결제를 붙이기 전에는 반드시 있어야 한다. 손님 캐릭터에 돈을 쓰게 하면 기기를 바꾸는 순간 잃는다.

## 지금 상태

- 브라우저가 처음 접속할 때 무작위 값(토큰)을 만들어 브라우저 저장소에 넣는다.
- 서버는 그 값의 해시를 열쇠로 캐릭터를 저장한다. 토큰 원문은 저장하지 않는다.
- 같은 토큰으로 다시 들어오면 캐릭터를 이어받고, 이미 접속 중이면 앞선 연결을 끊는다.

지금 구조에서 생기는 문제:

| 상황 | 결과 |
|---|---|
| 브라우저 저장소를 지운다 | 캐릭터를 잃는다. 되찾을 방법이 없다 |
| 다른 기기나 다른 브라우저로 들어온다 | 새 캐릭터가 된다 |
| 시크릿 창으로 들어온다 | 창을 닫으면 사라진다 |
| 토큰이 남에게 알려진다 | 그 사람이 내 캐릭터로 들어온다. 바꿀 방법이 없다 |
| 한 사람이 저장소를 지우며 반복 접속한다 | 캐릭터가 계속 새로 생긴다 (막을 수단이 없다) |
| 하루 중에 이름을 바꾼다 | (2026-11 고침) 순위와 '오늘의 등탑지기'는 이름이 아니라 저장 키로 센다 |

## 기기 옮기기 (2026-11-26, 계정이 생기기 전의 자리)

계정은 아직 보류다. 그 사이에 "다른 기기로 옮기기"만 넣었다. 비밀번호도 이메일도 받지 않는다.

- 흐름: 메뉴의 '기기' 탭에서 **코드 받기** → 8자 코드(헷갈리는 0 O 1 I L 없음, 10분, 한 번) → 다른 기기의 첫 화면(직업 고르기 창의 '코드로 이어받기') 또는 같은 탭에 넣는다 → 서버가 **새 토큰**을 그 기기에 주고, 그 기기는 그것을 간직하고 다시 접속한다. 옛 기기는 끊기고(4001) 자기 토큰을 지운다. 옛 토큰으로는 더 들어오지 못한다.
- 저장 키: 캐릭터의 저장 키(처음 토큰의 해시)는 **바꾸지 않는다.** 길드 명단·거래소·우편·던전 같은 곳이 그 키로 사람을 가리키기 때문이다. 대신 '토큰 해시 → 저장 키'의 별칭과 '물러난 토큰 해시'를 월드 저장(`handoff` 칸)에 둔다. 위 데이터 표의 `characters`가 '손님 토큰 해시'를 캐릭터 번호와 따로 두는 것과 같은 방향이다: 계정을 만들 때 이 별칭이 그 칸으로 옮겨 간다.
- 막는 것: 틀린 코드는 접속 주소와 사람마다 10분에 5번까지. 살아 있는 코드는 **코드의 해시만** 월드 저장(`handoff` 칸의 `codes`)에 남아 서버를 다시 켜도 끝날 때까지 쓰인다(2026-11-26 `feat/limits`. 그 전에는 메모리에만 있었다). 틀린 시도의 수는 메모리에만. 손님(저장소를 못 쓰는 브라우저)은 옮길 수 없다.
- 위 표에서 풀리는 것: "다른 기기나 다른 브라우저로 들어온다"(코드로 옮긴다), "토큰이 남에게 알려진다"(스스로 코드를 받아 새 기기로 옮기면 옛 토큰이 무효가 된다). 풀리지 않는 것: 저장소를 지운 뒤 되찾기(코드를 받을 기기가 없다), 시크릿 창, 반복 생성.
- 위험: 코드를 남에게 알려 주면 그 사람이 캐릭터를 가져간다(화면에 적어 두었다). 10분 안에 맞힐 확률은 31^8 ≈ 8.5×10^11 가운데 시도 수만큼이라 작다.
- 운영의 제재(차단·말 막기)는 저장 키에 걸리므로 기기를 옮겨도 따라간다. 관리자 통로는 [making-a-game.md](making-a-game.md) 9절.

## 목표와 범위

목표:

1. 캐릭터를 잃지 않는다: 기기를 바꾸거나 저장소를 지워도 되찾는다.
2. 처음 시작하는 장벽을 높이지 않는다: 로그인 없이도 시작한다.
3. 남이 내 캐릭터로 들어오지 못한다.
4. 제재가 가능하다: 문제를 일으킨 사람을 계정 단위로 막는다.

이번 설계에 넣지 않는 것:

- 한 계정에 캐릭터 여러 개. 자리는 만들어 두되 처음에는 계정당 하나다.
- 결제, 친구 목록, 길드. 계정이 생긴 뒤에 그 위에 얹는다.

## 흐름

### 처음 온 사람

지금과 같다. 토큰이 만들어지고 손님으로 시작한다. 화면 어딘가에 "계정에 연결하면 캐릭터를 지킬 수 있습니다"가 보인다. 강요하지 않는다.

연결을 권하는 때:

- 메인 퀘스트 1장을 마쳤을 때 (애착이 생긴 뒤).
- 레벨이 일정 수준을 넘었을 때.
- 결제 화면에 들어가려 할 때 (이때는 반드시).

### 손님에서 계정으로

1. "계정에 연결"을 누른다.
2. 로그인 서비스의 화면으로 갔다가 돌아온다.
3. 서버가 그 로그인 정보로 계정을 찾는다.
   - 계정이 없으면: 새 계정을 만들고 지금 손님 캐릭터를 그 계정에 붙인다.
   - 계정이 있고 캐릭터도 있으면: 어느 캐릭터를 쓸지 묻는다 (아래 "겹칠 때").
4. 이후에는 토큰이 아니라 로그인 세션으로 들어온다.

### 다른 기기에서

"로그인"을 누르고 같은 서비스로 로그인하면 계정의 캐릭터로 들어온다. 그 기기에서 손님으로 조금 해 둔 캐릭터가 있었다면 역시 어느 쪽을 쓸지 묻는다.

### 겹칠 때

계정에 이미 캐릭터가 있는데 지금 기기에 손님 캐릭터도 있는 경우다. 합치지 않고 고르게 한다. 두 캐릭터의 이름, 레벨, 직업, 마지막 접속 시각을 보여 주고 하나를 고른다. 고르지 않은 쪽은 30일 동안 보관하다가 지운다.

합치지 않는 이유: 불씨와 골드를 더하게 하면 손님 캐릭터를 여러 개 키워서 합치는 방법으로 재화를 불릴 수 있다.

## 로그인 수단 비교

| 수단 | 이용자가 하는 일 | 우리가 책임질 것 | 만들 양 | 비고 |
|---|---|---|---|---|
| 소셜 로그인 | 버튼 한 번 (이미 로그인돼 있으면) | 로그인 서비스가 준 식별자만 보관 | 적음 | 서비스마다 개발자 등록과 심사가 필요하다. 국내 이용자가 주로 쓰는 서비스와 해외 이용자가 쓰는 서비스가 다르다 |
| 이메일 링크 | 이메일을 넣고, 받은 링크를 누른다 | 이메일 주소 보관, 메일 발송 | 중간 | 메일 발송 서비스가 필요하다 (비용). 메일이 늦거나 스팸함에 들어가면 막힌다 |
| 아이디와 비밀번호 | 가입 양식 작성 | 비밀번호 해시 보관, 찾기와 재설정, 유출 대응 | 많음 | 책임이 가장 크다. 비밀번호 찾기에 결국 이메일이나 본인인증이 필요하다 |

권장: 소셜 로그인으로 시작한다. 한국어와 영어를 함께 내는 게임이라, 국내에서 널리 쓰는 것 하나와 해외에서 널리 쓰는 것 하나를 두면 대부분을 덮는다. 구체적으로 어느 서비스인지는 정해야 한다.

모바일 앱으로 감싸서 스토어에 올릴 계획이 있다면, 스토어가 요구하는 로그인 수단이 따로 있을 수 있다. 스토어 정책을 확인해야 한다.

## 데이터

지금은 `players` 표 하나에 토큰 해시를 열쇠로 캐릭터를 넣는다. 바꾼 뒤:

| 표 | 내용 |
|---|---|
| `accounts` | 계정. 번호, 만든 시각, 상태(정상, 정지), 정지 사유와 기한 |
| `identities` | 로그인 수단. 어느 서비스의 어느 식별자가 어느 계정인지. 계정 하나에 여러 수단을 붙일 수 있다 |
| `characters` | 캐릭터. 번호, 계정 번호(손님이면 비어 있음), 손님 토큰 해시(계정에 붙으면 비움), 이름, 저장 내용, 마지막 접속 |
| `sessions` | 로그인 세션. 세션 값의 해시, 계정 번호, 만든 시각, 만료 시각, 마지막 사용 |

- 로그인 서비스에서 받는 것은 식별자 하나면 된다. 이메일이나 프로필 사진은 받지 않는다. 받지 않은 것은 유출될 수 없고, 개인정보 처리의 범위도 줄어든다.
- 캐릭터에 번호가 생기므로 '오늘의 등탑지기' 명단을 이름이 아니라 캐릭터 번호로 셀 수 있다.

## 접속 절차

지금: 브라우저가 WebSocket으로 `join`에 토큰을 실어 보낸다.

바꾼 뒤:

1. 로그인은 일반 HTTPS 요청으로 한다. 성공하면 서버가 세션 값을 쿠키로 내려 준다 (스크립트에서 읽을 수 없고, HTTPS에서만 보내는 쿠키).
2. 게임에 들어갈 때 브라우저가 서버에 "접속권"을 요청한다. 서버는 세션(또는 손님 토큰)을 확인하고, 1분 동안만 쓸 수 있는 한 번짜리 접속권을 준다.
3. 브라우저가 WebSocket으로 `join`에 접속권을 실어 보낸다. 서버는 접속권을 확인하고 지운다.

접속권을 따로 두는 이유: 오래 쓰는 세션 값을 게임 연결에 직접 싣지 않기 위해서다. 그리고 나중에 게임 서버를 여러 대로 나눌 때, 로그인을 맡는 서버와 게임을 돌리는 서버를 분리할 수 있다.

## 지켜야 할 것

- **토큰과 세션은 해시로만 저장한다.** 지금도 토큰은 그렇게 한다.
- **세션에는 만료가 있다.** 오래 쓰지 않으면 끊고, "모든 기기에서 로그아웃"을 둔다.
- **로그인 시도에 횟수 제한을 둔다.**
- **돌아오는 주소를 검증한다.** 로그인 서비스에서 돌아올 때 우리가 보낸 요청이 맞는지 확인한다 (위조 요청 방지).
- **같은 캐릭터의 동시 접속은 하나만.** 지금처럼 나중 접속이 앞선 연결을 끊는다.
- **손님 캐릭터가 무한히 쌓이지 않게 한다.** 일정 기간 접속이 없고 진행이 거의 없는 손님 캐릭터는 지운다. 같은 주소에서 손님 캐릭터를 만드는 횟수에 제한을 둔다.
- **정지는 계정 단위로 한다.** 손님은 정지할 대상이 약하므로, 대화처럼 남에게 영향을 주는 기능은 계정에 연결한 사람에게만 여는 방법을 검토한다.

## 확인이 필요한 것 (전문가에게)

법률 자문이 아니다. 아래는 계정을 만들면 생기는 의무의 목록이고, 정확한 요건은 전문가에게 확인해야 한다.

- 개인정보 처리방침과 수집 동의. 로그인 서비스의 식별자만 받아도 개인정보에 해당할 수 있다.
- 만 14세 미만 이용자의 법정대리인 동의.
- 결제를 붙일 때의 본인인증과 미성년자 결제 관련 요건.
- 회원 탈퇴와 자료 삭제 요청에 대한 처리 기한과 방법.
- 해외 이용자를 받을 때 적용되는 다른 나라의 규정.
- 각 로그인 서비스의 이용 약관과 심사 요건 (게임에 쓸 때의 조건).

## 코드에서 바뀌는 곳

구조상 통신과 저장 계층만 바뀌고, 게임 규칙(`engine/server/game/`)은 바뀌지 않는다. (경로는 2026-11-27의 것. 인증은 묶음 2의 접점 `AuthProvider`(화면)·`ServerAuth`(서버, `engine/server/net/auth.ts`)에 새 구현을 꽂는 방식이 된다.)

| 곳 | 바뀌는 것 |
|---|---|
| `engine/server/store/` | `loadPlayer(열쇠)`가 캐릭터 번호 기준이 된다. 계정, 로그인 수단, 세션을 다루는 메서드가 더해진다. SQLite 구현에 표가 늘어난다 |
| `engine/server/net/` | 로그인과 접속권을 다루는 HTTP 경로가 생긴다. `join`이 접속권을 받는다 |
| `engine/shared/protocol.ts` | `join`의 `token`이 접속권으로 바뀐다 |
| `engine/client/net.ts`, `engine/client/platform/auth.ts` | 접속 전에 접속권을 받아 온다 (`AuthProvider`) |
| `engine/client/hud/` | 계정 연결과 로그인 화면, 캐릭터 고르기 화면 |
| `engine/client/i18n/` | 새 문장 |
| 저장 파일 | 지금의 손님 캐릭터를 새 표로 옮기는 변환이 한 번 필요하다. 토큰 해시를 그대로 손님 열쇠로 쓰므로 기존 캐릭터는 이어진다 |

## 구현 순서 (정해진 뒤)

1. 저장 계층을 캐릭터 번호 기준으로 바꾸고, 기존 저장 파일을 옮긴다. 이 단계까지는 이용자에게 달라지는 것이 없다.
2. 접속권 절차를 넣는다. 손님도 이 절차로 들어오게 한다.
3. 로그인 수단 하나를 붙이고 "계정에 연결"을 넣는다.
4. 다른 기기에서 로그인, 겹칠 때 고르기.
5. 세션 관리(로그아웃, 만료), 계정 정지.
6. 명단과 신고를 캐릭터 번호와 계정 기준으로 바꾼다.

## 정할 것

- [ ] 어느 로그인 서비스를 쓸지 (국내용, 해외용). 서비스마다 개발자 등록이 필요하고, 사업자 정보를 요구하는 곳이 있다.
- [ ] 손님에게 대화를 허용할지, 계정에 연결한 사람에게만 열지.
- [ ] 접속이 없는 손님 캐릭터를 며칠 뒤에 지울지.
- [ ] 계정당 캐릭터 수 (처음에는 하나를 권한다).
- [ ] 앱으로 감싸서 스토어에 올릴 계획이 있는지 (로그인 수단 선택에 영향을 준다).
- [ ] 개인정보 처리방침과 약관을 누가 쓰고 검토할지.
