# 인프라 스펙과 부하 측정

2026-11-23에 잰 결과와, 그 숫자에 근거한 단계별 구성이다. 서버 사양과 비용은 아직 정하지 않았다: 아래 "정할 것"에 적었다.

## 결론

- **서버 한 대(프로세스 하나)로 동시 접속 200명까지는 여유가 있고, 300명이 한곳에 모이면 한계에 가깝다.** 500명은 버티지 못한다.
- **먼저 막히는 것은 CPU가 아니라 전송이다.** 게임 계산은 300명에서도 틱당 2ms인데, 접속자마다 보낼 내용을 만드는 데 46ms가 든다.
- **전송량이 크다.** 300명이 모이면 서버가 초당 약 21MB(약 170Mbps)를 내보내고, 접속자 한 명이 초당 약 70KB(약 0.56Mbps)를 받는다. 모바일 데이터로는 부담스러운 양이다.
- 검증판(20~50명)은 지금 구조 그대로 충분하다. 출시판에서 수백 명을 받으려면 전송 형식을 바꿔야 한다.
- (2026-11-26) WebSocket 압축을 기본으로 켰다: 회선에 나가는 양이 약 1/4이 되고, 50명에서 CPU를 코어의 8%p쯤 더 쓴다. 아래 '압축'.
- (2026-11-26, 가지 `feat/loadtest`) 영웅이 함께 싸우는 수집형(사람마다 영웅 4~8)과 장시간 운영을 쟀다: 아래 '부하와 장시간'. 사람마다 따로인 단계에서는 200명 × 영웅 8(엔티티 약 2,300)도 틱 4.7ms·전송 14ms로 여유가 있고, **막히는 것은 들판에 영웅까지 한곳에 모일 때의 전송량**이다(100명 × 영웅 8이 모이면 1인 67KB/s). 틀을 고쳐 틱 시간이 등불지기 200명에서 8.1 → 2.4ms, 영웅 들판 200명 단계에서 5.5 → 3.4ms가 되었다(게임의 결과와 줄 위의 바이트는 그대로).

## 측정 방법

`npm run load`로 다시 잴 수 있다 (`test/load.ts`, `test/load-clients.ts`).

- 서버는 측정 프로세스 안에서 띄우고, 가짜 접속자는 다른 프로세스에서 실제 WebSocket으로 붙는다.
- 가짜 접속자는 1~3초마다 한 번 행동한다. 실제 사람보다 부지런하게 잡은 값이다.
- 시나리오당 15초, 그중 자리를 잡은 뒤의 12초를 잰다.
- 방식:
  - `cluster`: 모두 등탑 주변에 모인다. 서로가 서로의 시야에 들어서 전송량이 가장 크다.
  - `fight`: 모여서 습격을 막는다. 적과 전투 사건이 더해진다.
  - `spread`: 월드 전체로 흩어진다. 다만 15초로는 등탑에서 멀리 퍼지지 못해서 결과가 `cluster`와 비슷하게 나왔다. 흩어진 상태의 숫자로 읽으면 안 된다.

측정한 기계: AMD Ryzen 7 2700X(2018년 데스크톱 CPU), Windows 11, Node 22.15. 클라우드 서버의 코어 하나는 이보다 느릴 수도 빠를 수도 있어서, 실제 서버에서 다시 재야 한다.

읽는 법:

- **틱 지연**의 평균 6~7ms는 부하가 아니라 Windows 타이머의 정밀도(약 15ms 단위) 때문이다. 이 값이 그보다 눈에 띄게 커지면 서버가 밀리는 것이다. 300명 `fight`에서 최대 94ms, 500명에서 평균 129ms가 그 경우다.
- **전송 준비 시간**은 인원의 제곱에 가깝게 늘어난다. 모인 사람이 2배면 보낼 대상도 2배, 한 사람에게 보낼 내용도 2배이기 때문이다.
- 500명 행의 1인당 전송량이 줄어든 것은 서버가 밀려서 덜 보냈기 때문이지 좋아진 것이 아니다.
- 메모리는 문제가 되지 않는다.

## 측정하다 고친 것

1. **틱 루프가 Windows에서 느리게 돌고 있었다.** 50ms마다 부르게 했는데 실제로는 62ms쯤마다 불려서 초당 20번이 아니라 16번쯤 돌았다. 늦은 만큼 다음 대기를 줄이도록 고쳤다.
2. **전송 준비 시간을 절반으로 줄였다.** 엔티티 상태를 접속자마다 다시 문자열로 만들던 것을 한 번만 만들어 나눠 쓰게 했고, 지난번과 상태가 같은 엔티티(서 있는 캐릭터)는 다시 보내지 않게 했다.

| 인원 (cluster) | 고치기 전 전송 준비 ms (평균) | 고친 뒤 |
|---|---|---|
| 100 | 13.96 | 8.43 |
| 200 | 43.17 | 23.78 |

고치기 전에는 300명에서 틱 지연이 평균 141ms였다 (고친 뒤 9ms).

전송량은 이 측정에서 크게 줄지 않았다. 가짜 접속자가 쉬지 않고 움직여서 "서 있는 캐릭터"가 거의 없기 때문이다. 마을에 서 있는 사람이 많은 실제 상황에서는 더 줄 것으로 보지만, 재지는 않았다.

## 측정 뒤에 더한 것

길찾기(격자 A*)를 넣은 뒤 200명 `fight`를 다시 쟀다. 틱 계산이 평균 1.54ms에서 2.02ms가 됐고, 전송 준비 시간과 전송량은 그대로다. 경로 탐색 한 번은 평균 0.36ms, 최대 2.3ms다. 위 결과 표는 길찾기를 넣기 전의 숫자다.

## 부하와 장시간 (2026-11-26, 가지 `feat/loadtest`)

### 재는 도구

- `npm run load:game -- <게임> <인원[,인원…]> <초> [이름=값 …]` (`scripts/load.mjs`): 그 게임의 진짜 서버(`startServer`)를 한 프로세스(`scripts/load/server.ts`, 게임의 tsconfig로)에 띄우고, 다른 프로세스(`scripts/load/clients.mjs`)의 가짜 접속자를 실제 WebSocket으로 붙인다. 게임: `deungbul`, `dalmuri`, `collect`(틀의 시험용 내용 '영웅 들판'), `rollball`, `sample`, `cave`, `starmine`, `bastion`. 이름=값: `mode=stage|field|fight|spread`, `squad=N`(사람마다 영웅 N을 주고 편성), `bots=N`, `speed=X`(가상 시계 `g.now`의 배속: 날짜·출석·열쇠 채움·습격 시각), `start=ISO`, `churn=초`(그 간격마다 한 사람이 끊고 다시 접속), `db=sqlite`(`data/load/<이름>/`), `metrics=0`(운영처럼 구간 지표를 읽지 않는다), `port=0`, `compress=0`, `prof=폴더`(CPU 프로필), `out=파일`, `verbose=1`. 기본 포트는 3017이다.
- 결과 표의 칸: 틱 ms는 서버가 `game.tick`을 감싸 잰 모든 틱(평균/95%/99%/최대), 전송 ms·지연은 `server.metrics()`의 구간 값, 보낸 KB/s는 `/metrics`의 압축 전 글자와 회선 바이트, CPU는 서버 프로세스(압축 일꾼 스레드 포함, 코어 하나 = 100%). 서버는 지표 줄(JSON)도 남긴다: 엔티티의 종류별 수, 인스턴스 층의 수, 게임과 시스템(한 단계 아래까지)이 든 Map·Set·배열의 크기, 살아 있는 타이머·핸들의 수(`process.getActiveResourcesInfo`). 장시간 측정에서 쌓이기만 하는 것을 이것으로 찾는다.
- `node scripts/load.mjs bench <게임> <인원> <틱> [squad=N] [mode=stage|field]` (`scripts/load/bench.ts`): 통신 없이 한 프로세스에서 정해진 시계·난수로 틱과 사람마다의 스냅샷만 셈하고, 모든 스냅샷 글자·끝의 엔티티·저장을 묶은 지문(sha)을 찍는다. 틀을 고친 전후의 지문이 같으면 게임의 결과와 줄 위의 글자가 같다.
- 빠른 회귀 검사는 `npm test`에 있다: `collect/load`(사람 13 × 영웅 4가 단계와 들판에서 400틱: 틱 평균 8ms·전송 한 번 20ms의 넉넉한 상한, 그리고 아래 색인들이 예전 셈과 같은 답), `fx/hotpath`(장애물 밀어내기 6만 자리, 측정 값의 상한, 상태 글자). 무거운 측정은 넣지 않았다.

읽는 법:

- **단계(사람마다 따로인 층)는 가볍다.** 한 사람이 보는 것이 제 영웅과 그 단계의 적뿐이라 1인 0.4~0.5KB/s(회선)다. 200명 × 영웅 8(엔티티 약 2,300)에서 틱 4.7ms, 전송 14ms로 전송 주기(100ms)의 1/4쯤을 쓴다.
- **들판에 모이면 영웅이 보이는 엔티티를 5~9배로 늘린다.** 100명이 영웅 8씩 데리고 한곳에 서면 한 사람이 900개를 보고, 1인 67KB/s(회선, 압축 뒤), 서버 전체 6.7MB/s, CPU 코어 2.3개(대부분 압축 일꾼)다. 전송 준비는 인원의 제곱으로 는다(200 × 4에서 31ms).
- 고친 뒤에도 전송 시간의 큰 몫은 메시지마다의 소켓 쓰기다(아래 '고치지 않은 것').

### 장시간 운영

- 날짜가 바뀌는 것: 저장된 캐릭터의 일일 임무는 11-30의 것으로 새로 시작했고, 출석 연속 일수가 4(11-27~30), 달무리의 열쇠가 11-30에 채워졌다. 오류 로그는 없다.
- **찾아 고친 새는 곳 하나**: 서버의 측정 구간 값(`server.ts`의 `m.tick`·`m.flush`·`m.lag`)은 `metrics()`가 읽을 때만 비워지는데, 그것을 부르는 것은 `METRICS` 로그와 부하 도구뿐이다. 운영은 `METRICS`를 켜지 않으므로 틱마다 값이 쌓였다: 초당 50개(틱 20·지연 20·전송 10), 하루 약 430만 개, 배열의 여유까지 **하루 35~50MB, 일주일이면 수백 MB**. 35분의 측정에서는 1MB 남짓이라 메모리 곡선에는 보이지 않아 코드를 읽어 찾았다. 이제 72,000개(약 1시간)를 넘으면 오래된 반을 버린다(`ops.ts`의 `pushCapped`, 시험 `fx/hotpath`).
- 재지 않은 것: 실제 시간으로 며칠(가상 시계는 날짜만 빠르게 돌고 게임 안의 초는 그대로다), 접속자 수백 명의 장시간, 자동 백업이 도는 장시간(측정에서는 껐다).

### 고치지 않은 것 (제안)

- **메시지마다의 소켓 쓰기**(줄 위가 바뀌는 것): 압축을 켜면 ws가 메시지를 하나씩 압축해 하나씩 쓴다. 200명 단계에서 서버 스레드의 약 25%가 `writev`다. 한 사람에게 가는 전송 한 번의 메시지(스냅샷·개인 상태·안내문)를 한 프레임으로 묶으면(프로토콜 4) 줄지만 줄 위의 바이트가 바뀐다.
- **남의 영웅을 덜 보내기**(줄 위가 바뀌는 것): 들판의 전송량은 남의 영웅이 대부분이다. 남의 영웅은 좁은 시야(예: 16m)나 낮은 빈도(초당 5번)로, 별·레벨(거의 바뀌지 않는 값)은 상태 줄이 아니라 들어올 때만 보내면 크게 준다. 이진 형식과 정수 좌표는 아래 '출시판' 표의 것 그대로다.
- `g.remove`는 없앨 때마다 엔티티 전부를 훑어 대상과 피해 준 사람을 지운다(단계의 몬스터가 많이 죽는 200명에서 서버 스레드의 약 2%). 거꾸로 된 색인이 필요해 두었다.
- 개인 상태는 전송마다 셈해(`squad`의 전투력 `squadView` 등) 지난 글자와 견준다(200명에서 약 2%). 시스템마다 바뀜 표시(`dirty`)를 다는 일이라 두었다.

## 재지 않은 것

- 흩어져 있을 때의 전송량 (측정이 짧아서 퍼지지 못했다).
- 실제 클라우드 서버에서의 성능.
- 실제 네트워크(지연, 손실)를 거칠 때의 체감. 모두 같은 기계 안에서 쟀다.
- 브라우저 쪽 성능: 한 화면에 수십 명이 보일 때의 프레임 수, 특히 모바일.
- 몇 시간 이상 켜 두었을 때의 메모리 증가. (2026-11-26: 실제 35분·가상 56시간을 쟀다. 위 '부하와 장시간'. 실제 시간으로 며칠은 아직)
- SQLite 저장이 몰릴 때의 영향 (접속자가 한꺼번에 나갈 때). 저장은 이제 한 묶음(트랜잭션)이라 캐릭터마다 따로 쓰던 때보다 디스크 쓰기가 적을 것으로 보지만 재지 않았다.
- 자동 백업(VACUUM INTO)이 큰 DB에서 틱을 얼마나 멈추는지. 지금 운영 DB(수백 KB)는 수 ms다. 동기로 도므로 DB가 수백 MB가 되면 다시 잰다.

## 운영의 바탕: 점검, 공지, 원격 설정 (2026-11-27, 가지 `feat/ops2`)

틀의 쓰는 법은 [making-a-game.md](making-a-game.md) 16절. 여기는 운영 서버에서 하는 차례다. 명령은 모두 **운영 서버가 도는 PC에서** 저장소 뿌리에서 친다(관리자 통로는 같은 PC만 받는다). 게임을 적지 않으면 등불지기(포트 3001)다. 예제는 `npm run admin -- sample …`.

### 점검하는 법

1. 예고: 점검 30분 이상 앞에 한다. 시각은 서버 PC의 현지 시각으로 읽는다(초기화 시각 `RESET`의 시간대).
   ```
   npm run admin -- maint plan "2026-12-01 09:00" --for 1h --ko 서버 옮기기 점검 --en Server move
   npm run admin -- notice add --from now --to "2026-12-01 10:00" --ko "12월 1일 09:00~10:00 점검합니다." --en "Maintenance on Dec 1, 09:00-10:00 (KST)."
   ```
   접속한 화면 위에 카운트다운 띠가 생기고, 30·10·5·1분 전에 가운데 알림이 간다. `npm run admin -- maint`로 예고를 확인한다. 거두려면 `maint cancel`.
2. 점검 중에 들어가 볼 사람(관리자)을 적는다: 그 사람이 쓰는 브라우저의 캐릭터 이름으로 `npm run admin -- maint allow 이름`. 손님(저장되지 않는 캐릭터)은 적을 수 없다.
3. 시각이 되면 저절로 시작한다(바로 하려면 `maint now --for 30m`). 서버가 모두 저장하고 관리자 말고는 내보낸다(닫힘 4004). 화면은 '서버 점검 중입니다'와 예정 끝 시각을 보이고 1분마다 다시 접속해 본다. `npm run admin -- who`로 남은 사람을 본다. 상태 페이지(`/status.html`)도 '점검 중'이 된다.
4. 점검 동안 할 일을 한다. 서버를 다시 켜도(배포: `npm run build` 뒤 `node scripts/restart.mjs`) 점검 중으로 뜬다(점검의 상태는 DB의 `live` 표에 있다).
5. 끝: `npm run admin -- maint end`. 보상을 주려면 `maint end --gold 300 --item potion:3 --days 30`(최근 30일 안에 저장된 캐릭터 모두에게 '점검 보상' 우편. 접속해 있지 않은 사람은 다음 접속 때). 화면은 1분 안에 저절로 다시 들어온다. 예고 공지를 내린다: `notice`로 id를 보고 `notice del id`.

**리허설 기록(2026-11-27, 운영 DB 복사본, 임시 서버 3015)**: 예고(2분 뒤) → 카운트다운 띠 → 1분 전 가운데 알림 → 시각에 시작: 손님 브라우저는 저장되고 4004로 끊겨 점검 화면, 관리자 접속자는 남음, 토큰 없는 손님의 새 접속은 4004와 점검 안내 → `maint end --gold 50 --item potion:2 --days 30`: 보상 우편, 브라우저는 1분 안에 저절로 다시 들어와 우편함에 '점검 보상'. 자세히는 [framework-status.md](framework-status.md)의 '운영의 바탕'.

### 공지

- 올리기: `npm run admin -- notice add [--popup] [--ticker] [--from 시각] [--to 시각 | --for 기간] --ko 글 [--en 글]`. 창(`--popup`: 접속할 때 한 번)과 띠(`--ticker`: 화면 위에서 흐름)를 고르지 않으면 둘 다. 시작을 적지 않으면 지금, 끝을 적지 않으면 24시간.
- 예약: `--from "2026-12-24 18:00" --to "2026-12-26 00:00"`. 시작 시각이 되면 접속한 사람에게도 뜬다.
- 목록과 내리기: `notice`, `notice del id`. 바로 한 줄만 알리려면 예전처럼 `announce 글`.
- 글은 300자까지, 언어마다. 영어를 적지 않으면 영어 화면에도 한국어 글이 보인다.

### 기능 깃발 (킬 스위치)

- 사고(복제 버그, 거래 사기)가 나면 그 기능을 먼저 끈다: `npm run admin -- flag market off`(거래소), `flag mail off`(우편 받기), `flag gacha off`(뽑기), `flag chat off`(대화), `flag join off`(새 접속: 들어와 있는 사람은 그대로). 꺼진 기능을 쓰면 화면에 '잠시 꺼져 있습니다'가 뜬다. 켜기: `flag market on`. 목록: `flag`.
- 깃발은 DB에 남는다: 다시 켜도 꺼진 채다. 공지를 함께 올린다.

### 원격 설정 바꾸기

- 바꿀 수 있는 칸은 게임이 내용의 `LIVE_KEYS`에 선언한 것뿐이다: `npm run admin -- set`으로 목록과 지금 값을 본다(등불지기는 아직 선언한 칸이 없다: 무엇을 열지는 사용자가 정한다).
- 바꾸기: `npm run admin -- sample set DAILIES.kill20.n 30`. 검사(처음 값과 같은 모양, 게임의 범위)를 지나야 반영되고, 재시작 없이 바로 든다. 화면도 읽는 칸이면 접속한 화면에도 간다.
- 되돌리기: `set 이름 --undo`(바로 앞 값), `set 이름 --reset`(소스의 값). 이력: `set --log [이름]`(누가·언제·전 → 후).
- 모든 명령은 예전처럼 `admin-audit.log`에도 남는다.

### 상태 페이지

- 서버가 빌드된 화면의 폴더(`dist/`)에 `status.json`과 `status.html`을 30초마다 쓴다: 터널 주소 뒤에 `/status.html`. 서버가 죽으면 '응답 없음'(마지막 시각이 90초 넘게 오래됨), 점검 중이면 '점검 중', 예고가 있으면 '점검 예정'과 시각.
- 게임 서버가 꺼져 있어도 보이게 하려면 `STATUS_DIR`로 다른 정적 호스팅의 폴더를 준다(그 폴더를 올리는 것은 따로). 끄려면 `STATUS=0`.
- 접속자 수는 5명 단위로 둥글린다(정확한 수는 `/healthz`·`/metrics`, 같은 PC에서).

## 화면 오류와 내 데이터 삭제 (2026-11-27, 가지 `feat/web2`)

외부 서비스 없이 게임 서버가 받는다(`engine/server/net/web.ts`, 쓰는 법은 [making-a-game.md](making-a-game.md) 17절). 명령은 서버가 돌고 있는 같은 PC에서 관리자 CLI로 보낸다(`npm run admin -- [게임] …`, 기록은 다른 관리자 명령처럼 `admin-audit.log`에 남는다).

### 화면 오류 보기

```
npm run admin -- errors            최근 20묶음 (같은 오류는 한 줄: 횟수, 종류, 문장, 페이지·빌드·브라우저, 처음·마지막 시각, 스택 3줄)
npm run admin -- errors 50 --all   50묶음, 스택 12줄 모두
npm run admin -- errors clear 1a2b3c4d5e6f   고친 오류의 묶음을 지운다 (서명의 앞부분도 된다)
npm run admin -- errors clear all
```

- 무엇이 오나: 화면의 처리되지 않은 오류(`error`), 처리되지 않은 Promise 거절(`rejection`), 그리기 장치를 잃음(`webgl`), 게임이 알린 것(`report`). 받는 곳은 `POST /client-error`(본문 8KB까지, 주소마다 10건 뒤로는 10초에 1건, 서버 전체 초당 1건). 저장은 SQLite의 `client_errors` 표(500묶음까지, 오래된 것부터 지운다).
- 개인정보: 주소의 호스트·쿼리·조각, 긴 16진(토큰), 이메일, IP, 6자리 넘는 숫자를 빼고 적는다. 접속 주소는 적지 않는다. 브라우저는 'Chrome 142 Windows'처럼만.
- 읽는 법: 횟수가 갑자기 는 묶음, 빌드(`index-<해시>.js`)가 새것인 묶음이 먼저다. `webgl`이 많으면 그래픽 품질의 기본값(설정 창)을 낮출지 본다. 같은 오류가 다른 빌드에서 이어지면 서명이 같아 한 줄로 모인다(파일 이름의 해시와 줄 번호는 서명에 넣지 않는다).

### 내 데이터 삭제 요청 처리

사람이 설정 창에서 요청하면 `PRIVACY.eraseDays`(기본 7일) 뒤에 서버가 저절로 지운다(1분마다 살핀다, 켜질 때 한 번). 운영자가 할 일은 대개 없다. 메일 등 게임 밖으로 요청을 받았을 때:

```
npm run admin -- erase                 기다리는 요청 (이름, 키 앞부분, 요청·실행 시각)
npm run admin -- erase ask 아무개      대신 요청을 받는다 (유예는 게임의 기본. 일수를 붙이면 그만큼: erase ask 아무개 0이면 다음 살필 때)
npm run admin -- erase cancel 아무개   요청을 거둔다 (본인이 취소를 부탁했을 때)
npm run admin -- erase now 아무개      유예 없이 곧바로 지운다 (법적 요구, 본인 확인을 마친 경우)
npm run admin -- erase log 50          기록: 지움·취소·기다림, 키 앞부분, 시각 (지운 사람의 이름은 남지 않는다)
npm run admin -- erase sweep           때가 된 요청을 지금 실행 (서버가 1분마다 한다)
```

- 본인 확인: 계정이 없으므로 '그 캐릭터의 기기'에서 설정 창으로 요청한 것이 곧 확인이다. 게임 밖 요청은 기기 옮기기 코드를 받게 해(그 기기에서만 만들 수 있다) 확인하는 것을 권한다 [추정: 정책은 정할 것].
- 지우면: 접속을 끊고(닫힘 4010), 캐릭터 저장·동의 기록·기기 옮기기 별칭·맡아 둔 우편·거래소에 올린 물건을 지우고, 길드 명단에서 뺀다. 신고 기록과 차단·말 막기는 이름만 지우고 남긴다(제재 근거). 관리자 감사 기록과 경제 장부(사람 구분 없는 합계)는 그대로다. 표는 [making-a-game.md](making-a-game.md) 17절.
- **백업**: 자동 백업(`backup/auto-*.db`)에는 지우기 전의 저장이 남는다. 백업은 20개(기본 6시간마다)를 넘으면 오래된 것부터 지워지므로 약 5일 뒤에는 모두 빠진다. 백업에서 되돌릴 때는 그 뒤에 실행된 삭제(`erase log`)를 다시 실행한다.

## 신고 보기와 금칙어 관리 (2026-11-27, 가지 `feat/social3`)

사회와 안전(`engine/server/net/social.ts`, 쓰는 법은 [making-a-game.md](making-a-game.md) 18절)의 운영 몫. 명령은 서버 PC에서 관리자 CLI로 보낸다(`npm run admin -- [게임] …`, 모두 `admin-audit.log`에 남는다).

### 신고 보기

```
npm run admin -- reports            처리하지 않은 신고 20건: 신고한 사람 → 당한 사람, 채널, 당한 사람의 최근 말, 문맥 세 줄(신고한 줄과 그 앞뒤)
npm run admin -- reports 50 --all   처리한 것까지
npm run admin -- report mwyxmw      신고 하나의 전부: 두 사람의 키 앞부분, 최근 말, 대화의 앞뒤 줄 전부 (> 당한 사람의 말, ▶ 신고한 줄). id는 앞부분만 적어도 된다
npm run admin -- blocks 아무개      그 사람이 차단한 사람 (서로 차단한 다툼인지 볼 때)
npm run admin -- resolve mwyxmw 경고함   처리했다고 표시
npm run admin -- mute 아무개 24h 욕설    (제재는 예전과 같다: mute, ban …)
```

- 문맥은 서버가 기억한 대화 줄(30분, 400줄) 가운데 **신고한 사람이 본 줄만**이다: 남의 귓말·다른 파티·다른 길드의 말은 들지 않는다. 원문(가리기 전)이 적힌다. 시각은 UTC.
- 사람을 눌러 한 신고(줄을 고르지 않은 것)는 그 사람의 마지막 말의 앞뒤가 붙는다. 서버를 다시 켜면 기억한 줄은 비지만 이미 적힌 신고의 문맥은 DB에 남는다.
- 차단은 운영자가 할 일이 없다: 사람마다 서버에 저장되고(저장 키 단위, 이름을 바꿔도 이어진다) 서버가 거른다. 예전 화면이 브라우저에 남긴 차단 목록은 그 사람이 처음 접속할 때 서버로 옮겨진다(서버 로그 `[social] 옛 차단 목록을 옮겼습니다`).

### 금칙어 관리

```
npm run admin -- words                     금칙어 개수, 관리자가 더한 낱말
npm run admin -- words test 씨 1 발 ㅋㅋ    그 글이 어떻게 펴지고(자모·덩어리) 대화에서 어떻게 가려지는지, 이름으로 쓸 수 있는지
npm run admin -- words add 새욕설 다른말    더한다: 곧바로 걸리고, 운영 값(DB의 live_meta)에 남아 다시 켜도 걸린다
npm run admin -- words del 새욕설          관리자가 더한 목록에서 뺀다 (이미 걸고 있는 것은 서버를 다시 켜면 풀린다)
```

- 틀의 목록(`BASE_BANNED`, 한·영 짧은 것) + 게임이 서버 진입점에서 더한 것(`addBannedWords`) + 관리자가 더한 것. 우회 표기(띄어쓰기·특수문자·자모 분리·전각·늘인 소리·되풀이·숫자/기호·영문 자판·닮은꼴)는 펴서 견주므로 변형을 따로 적지 않는다: `words test`로 확인한다.
- 잘못 막는 말이 신고되면: 그 낱말을 품은 보통 말을 게임의 서버 진입점에서 `addAllowedWords`로 더한다(관리자 명령은 아직 없다). 이름은 대화보다 엄격하다(띄어 쓴 것도 이어 읽는다).
- 2026-11-27 측정(`$TEMP/dg-work/social3-tools/fuzz.ts`): 금칙어 무작위 변형 6,000개 중 놓침 0.42%(대부분 영문 자판 + 띄어쓰기·숫자를 겹친 것), 보통 문장 2,456개(틀·게임의 화면 문장 + 겹치기 쉬운 대화체) 중 대화로 잘못 막음 0.20%(`shiitake`, `Scunthorpe` 같은 영어 낱말 안의 욕, `개새로`), 이름으로 0.53%.

### 연령 (내용에 `AGE`를 적은 게임)

```
npm run admin -- age 아무개          그 사람의 답(태어난 해 또는 구간, 답한 날)과 제한 모드인지
npm run admin -- age 아무개 reset    답을 지운다: 다음 접속(접속 중이면 곧바로)에 다시 묻고, 그때까지 제한 모드
```

- 사람이 잘못 골랐다고 문의하면 reset. 답은 사람(지금은 저장 키) 단위로 `social_prefs`에 남는다. 본인확인·보호자 동의는 없다(결정이 필요하다).
