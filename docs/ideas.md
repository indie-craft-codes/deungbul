## 1. AI 채팅으로 게임하기

*2026-11-24, 사용자 아이디어.* 채팅창에 말로 적으면 AI가 알아듣고 게임을 대신 하거나 알려 준다.

### 하는 일
- **루틴 맡기기**: "물약 20개 될 때까지 늑대 잡고, 가방 차면 평범한 장비 분해하고, 밤 11시 습격 전엔 마을로 와" → 자동 사냥·이동·분해·상점 명령의 순서로 바꿔 돌린다.
- **정보 조회**: "불곰은 어디서 나와?", "지금 내 장비에서 뭘 바꾸면 제일 좋아?", "레벨 20까지 얼마나 남았어?" → 도감·내 상태·장비 비교로 답한다.
- 더 생각해 볼 것: 파티원 모으기 도움, 오늘 할 일 정리(일일 임무·출석·던전 횟수).

### 정해진 것: 무료 + 월정액
| | 무료 | 월정액 |
|---|---|---|
| 정보 조회 | 하루 몇 번 (도감·공용 함수로 바로 답하는 질문은 AI를 부르지 않고 횟수에서 뺀다) | 넉넉히 |
| 루틴 | 하나, 짧게 | 여러 개 저장·예약, 긴 루틴 |

- **편의만 판다.** 능력치·보상은 팔지 않는다. 루틴도 자리 비움 사냥과 같은 하루 몫 안에서만 돈다(사람보다 잘하는 봇이 되지 않게).

### 만드는 방향 (제안)
- **AI는 계획만, 실행은 서버가.** AI는 말을 "계획(규칙 목록)"으로 바꿀 때 한 번 부르고, 실행은 틀의 자동 사냥이 한다. 매 순간 AI가 조종하는 것보다 싸고(호출 수), 빠르고(지연), 안정적이다(서버 부하).
- **틀과 게임의 경계**: 명령 목록과 조회 함수를 AI에게 넘기는 통로는 틀에(어느 게임에나), 말투와 게임 고유 정보는 게임에.

### 틀에 이미 있는 바탕
- 자동 이동·자동 사냥·자리 비움 사냥: `engine/client/auto.ts`, `engine/server/game/systems/away.ts`.
- 서버 명령은 전부 `g.commands`의 이름 있는 명령이고 화면 동작은 `engine/client/actions.ts`에 모여 있다: AI가 부를 "도구 목록"으로 그대로 쓸 수 있다.
- 조회의 답을 만들 셈: 도감의 공용 함수(`engine/shared/defs/`)와 언어 파일, 장비 비교 `compareGear`, 필요 경험치 `needFor`, 재료 얻는 곳 `sourceLine`.

### 시작 전에 필요한 것
- 계정, 현금 결제와 자동 갱신(갱신 전에 알리고 해지는 쉽게), 남용 막기(하루 한도).
- 비용 측정: 사람당 하루 호출 수를 시험판에서 실제로 재서 월정액 값으로 감당되는지 본다.

## 2. 사용자가 만드는 코스튬과 거래

*2026-11-24, 사용자 아이디어.* 플레이어가 코스튬을 직접 만들어 게임 재화로 사고판다. 운영자가 수수료로 수익을 얻을 수 있는가.

### 결론
게임 재화(골드)로만 거래하면 수수료는 골드가 사라지는 것(물가 조절)일 뿐 **운영자의 돈이 되지 않는다**. 지금 거래소 수수료가 그렇다. 수익이 되려면 현금이 들어오는 지점이 있어야 한다.

### 수익 구조 후보
| | 방식 | 메모 |
|---|---|---|
| 가 | 현금으로 사는 유료 재화를 따로 두고, 코스튬은 그것으로만 사고판다. 판매액의 일부를 운영자가 가진다 | 제페토·로블록스 방식. 질문의 "수수료"에 가장 가깝다 |
| 나 | 거래는 골드로 두고, 만들기 도구·판매 칸·꾸미기 슬롯을 현금 상품으로 판다 | 법적으로 가장 단순하다 |
| 다 | 광고 | 단순하지만 수익이 작다 |

- 유료 재화와 골드는 섞지 않는다(골드로 유료 재화를 살 수 없게).

### 조심할 것
- **만든 사람에게 현금으로 정산**(로블록스 DevEx, 제페토 스튜디오 정산 같은 방식)은 한국 게임산업법의 환전·환전 알선 금지에 걸릴 수 있고, 세금·미성년자 결제·청약 철회와 얽힌다. **시작 전에 법률 검토가 필요하다.**

### 시작 전에 필요한 것
- 계정, 현금 결제.
- 코스튬 만들기 도구(로우폴리 부품·색 고르기), 신고·검수(저작권·선정성), 거래 기록.
- 틀과 게임의 경계: 코스튬 정의·만들기·거래 통로는 틀에, 값과 수수료율은 게임의 내용에.

## 3. AI로 만드는 캐릭터: 뽑기·수집형 RPG와 MMORPG의 변신을 잇기

*2026-11-26, 사용자 아이디어.* 지금 만드는 수집형·방치형 RPG 모듈(`roster`·`gacha`·`squad`·`stages`, 가지 `feat/collect`)과 MMORPG(등불지기 계열)의 뽑기를 하나로 잇는 방향.

### 하는 일
- **사용자가 캐릭터를 만든다**: 게임 안의 AI에게 프롬프트(말)로 설명하면 캐릭터(겉모습·이름·성격, 역할과 능력치의 틀 안에서)가 만들어진다.
- **무제한이 아니다**: 전 서버 합쳐 1주일에 몇 개처럼 만들 수 있는 수를 운영이 정한다(희소성, AI 비용, 검수량을 함께 조절).
- **사고팔 수 있다**: 만든 캐릭터를 다른 사용자가 살 수 있고, **수익은 만든 사람과 나눈다. 거래와 수익은 모두 게임 안 재화다(현금 아님, 사용자 결정 2026-11-26).**
- **두 장르에서 같은 캐릭터**: 수집형 RPG에서는 동료(편성해서 함께 싸움)로, MMORPG에서는 **변신**(그 캐릭터의 겉모습과 능력으로 바뀜)으로 쓴다. 한 사람의 소유가 두 게임에서 **같이 맞춰진다**(싱크).

### 정해진 것 (사용자 결정 2026-11-26)
- **현금이 아니라 게임 안 재화**로 사고팔고 나눈다. 판매액의 일부는 만든 사람에게, 나머지는 수수료로 사라진다(재화 회수). 현금 정산이 없어 환전 문제는 생기지 않는다.
- **검수는 게임 안의 프롬프트 요청에서 한다**: 사용자가 게임 안에서 보낸 프롬프트(요청)를 AI가 만들기 **전에** 검사해서, 실존 인물·기존 작품 캐릭터 흉내, 선정성·혐오 표현을 요청하면 만들지 않고 돌려보낸다(거절된 요청은 주간 한도를 쓰지 않는다). 만들어진 결과도 한 번 더 확인하고, 그 뒤로는 신고로 받는다.
  - **운영자 승인은 두지 않는다 (사용자 결정 2026-11-26)**: 사람이 매번 보기 힘들다. 대신 **요청 검사 → 결과 자동 확인 → 바로 공개 → 신고가 오면 운영자가 보고 회수**로 한다. 회수하면 그 캐릭터를 산 사람에게 낸 재화를 돌려주고(만든 사람의 몫도 되돌림), 반복해서 회수되는 사람은 만들기를 막는다. 틀에는 신고(이미 있는 신고·제재 통로를 캐릭터에도)와 관리자 명령 '회수'를 두면 된다.
- **밸런스는 기존 캐릭터의 범위 안에서 관리한다**: 등급마다 기존 캐릭터들의 능력치 범위를 정해 두고, AI가 만든 캐릭터는 그 범위를 넘지 못한다. 운영이 범위를 조절한다.

- **등불지기에는 쓰지 않는다 (사용자 결정 2026-11-27)**: 이 아이디어는 틀(`engine/`)의 기능으로 만들고, 쓰는 게임은 따로 정한다. 등불지기의 내용·경제는 바꾸지 않는다.

### 만드는 방향 (제안)
- **AI는 설명을 '정의'로 바꾸기만**: 프롬프트 → 정해진 칸의 캐릭터 정의(겉모습 부품·색, 역할, 능력치 배분, 이름). 능력치는 틀이 정한 한도 안에서만(돈으로 센 캐릭터를 만들지 못하게: 겉모습과 개성은 자유, 힘은 등급마다 같은 예산).
- **하나의 캐릭터 정의를 두 모듈이 읽는다**: 수집형 쪽은 `roster`의 영웅, MMORPG 쪽은 변신(새 모듈 `morph`: 겉모습을 바꾸고 능력치 보정을 `g.mods`로). 정의와 소유는 게임 밖의 공용 저장소(계정에 묶임)에 두고 두 게임 서버가 읽는다 = 싱크.
- **뽑기와의 관계**: 사용자가 만든 캐릭터를 뽑기 풀에 넣을지, 직접 거래만 할지 정해야 한다. 풀에 넣으면 확률 공개 의무(확률형 아이템 표시)가 그 캐릭터마다 걸린다.
- **주간 한도**: 전 서버 공용 카운터(주마다 초기화), 만들기 권한은 추첨·경매·순서 중 하나.

### 조심할 것
- **재화 흐름**: 판매 수익이 게임 재화로 쌓이므로, 인기 캐릭터를 만든 사람에게 재화가 몰린다. 수수료율과 만든 사람 몫을 경제 지표(`npm run econ`)로 보고 조절한다. 게임 재화를 현금으로 사게 하면 다시 [2. 코스튬](#2-사용자가-만드는-코스튬과-거래)의 법률 문제가 생긴다.
- **AI 생성물**: 요청 단계의 검사(위 '정해진 것')를 빠져나가는 우회 표현(돌려 말하기, 다른 언어, 띄어쓰기 바꾸기)이 있으므로, 결과의 확인과 신고·회수 절차를 같이 둔다. 거른 요청과 까닭은 기록해 검사 규칙을 고친다.
- **AI 비용**: 만들기 한 번의 호출 비용 × 주간 한도로 상한이 정해진다(한도가 비용 조절도 겸함).
- **밸런스**: 거래로 힘을 살 수 있으면 재화가 많은 사람이 세진다. 힘은 기존 캐릭터의 범위로 묶고 거래의 가치는 겉모습·희소성에 둔다.

### 틀에 이미 있는 바탕
*2026-11-27, 가지 `feat/chardef`([framework-status.md](framework-status.md)의 '캐릭터 정의와 변신', 쓰는 법은 [making-a-game.md](making-a-game.md) 15절).* AI가 내놓을 **정해진 형식의 캐릭터 정의**(`engine/shared/defs/chardef.ts`의 `CharDef`: id, 이름, 짧은 소개, 겉모습, 역할, 등급, 능력치 배분, 기술)와 그것을 믿지 않는 검증기 `validateCharDef`(모양·길이·제어 문자·쓸 수 있는 글자·없는 부품과 기술·등급마다의 능력치 예산(기존 영웅의 범위에서 셈할 수 있다)·크기 배율·금칙어 고리. 거절은 기계가 읽는 코드 26가지와 한국어·영어 문장)가 있다. 겉모습은 부품 체계(`engine/shared/defs/look.ts`: 칸 여섯마다 부품, 색 넷, 무늬, 크기. 틀의 기본 부품 34가지, 게임이 더하고 뺀다)로 그린다. 정의를 두는 모듈 `chars`(서버 DB의 월드 저장, 계정 공용 저장소로 바꿔 끼우는 `useStore`)가 `roster`와 함께면 정의를 영웅으로 쓰고, 변신 모듈 `morph`가 가진 정의의 겉모습(남에게도 보인다)과 게임이 정한 보정·시간·재사용 대기로 바꾼다. 예제(`games/sample`)에 손으로 쓴 정의 넷이 있다. 아직 없는 것: AI 생성기와 요청 검사, 계정과 소유의 싱크, 거래·수익 나누기, 주간 한도, 신고·회수의 관리자 명령(회수 자체는 `g.chars.remove`).

### 예제 게임으로 보인 것
*2026-11-27, 가지 `feat/hybrid` → 2판 `feat/pact2`.* 틀 위의 새 예제 **"메아리 계약"**(`games/echopact`, 포트 3003)이 이 아이디어를 **한 서버 안의 두 게임**으로 보였다(사용자 말: "두 게임을 왔다 갔다 하면서 하고 수집한 게 변신", "카드 능력치가 변신 능력치"). 게임 A **계약의 탑**(수집형: 뽑기·카드 키우기·편성·장 셋 × 단계 다섯, 단계 선택 화면과 보랏빛 탑의 장면)과 게임 B **울림골**(MMORPG: 들판의 사냥·장비·파티)을 화면의 '게임 바꾸기'로 싸우는 중에도 바로 오간다. 뽑은 메아리(손으로 쓴 캐릭터 정의)는 A에서 편성 동료로 싸우고, B에서는 따라다니지 않고 **변신 목록**이 되며, 변신한 동안의 체력·공격은 **A에서 키운 그 카드의 능력치**에서 셈한다(카드와 변신 탭에 같은 '변신 시 능력치'). 대화(전체·귓말·친구)는 두 게임이 하나다. **보이지 않는 쪽도 '자동'이면 돈다**: B에서 자동 사냥을 켠 채 A로 가면 들판에 몸이 남아 사냥하고(다른 사람에게도 보인다), A에서 싸우던 단계는 B로 가도 메아리만으로 끝까지·자동 진행이면 다음으로 간다. 보이지 않는 사냥에는 안전장치(물약·물러남·멈춤)와 다른 화면의 위험 알림·'바로 가기'가 있다. 처음 30분 시뮬레이션: 첫 뽑기 1분, 첫 10번 뽑기 18~19분, 두 쪽을 함께 돌리면 번갈아 할 때의 1.29배. 이것을 위해 틀에 일반 칸을 넣었다(게임 안의 모드 `modes`, 편성의 자리, 변신의 소유를 영웅에서 읽기·능력치 대체, 정의의 언어마다의 이름, 자동 사냥 안전장치, 층을 넘는 대화 채널). AI 생성·계정·진짜 두 서버의 싱크·거래는 하지 않았다. 수치·빈 곳·스크린샷은 [proof-echopact.md](proof-echopact.md).
